All work was done on a copy in /tmp/claude-1000/-home-jens-Projects-raindropchimes/4e199ce1-d2a0-47d9-bb6f-9e21b46c8d88/scratchpad/impl_composer_review (repo/ is the copy; `cmp` at the end confirmed the 17 reviewed files were still byte-identical to the repository). Nothing in the repository was touched.

What I ran:
- **The four checks:** check_10, check_11, check_12 and check_20 all exit 0, with the numbers the implementer reported (625 and 630 lines identical; 686,681 tones with 0 failures; 668/708/248/433 lines identical). They also exit 0 under `-fsanitize=address,undefined -fno-sanitize-recover=undefined`.
- **Warnings:** none under the required flags for the three sources and four helpers; the three sources are also clean under `-Wshadow -Wconversion -Wstrict-prototypes -Wmissing-prototypes`.
- **Line-by-line comparison:** slotwalk.c against Appendix A, section 9 and the v4, v6 and v10 sources. Draw order, moduli, the count d, the slot-free test, the end-phase boundary and the expression shapes all match, including `sin((PI*c)/(T-31))` multiplying before dividing and `(150*(density+0.05))/(1+r)`.
- **Later versions:** with v6-like and v10-like rule sets built only from `Rules` fields (later.c), the composer reproduces all seven later reference lists (two v5, two v6, three v10) exactly. Against freshly built traced v5, v6 and v10 programs (cross.sh), 400 runs each over 10 cycle counts from 32 to 777 gave 105,376 + 60,956 + 77,646 tone lines with 0 differences. So the continuous level rule and the `counted_above`, `first_reach`, `density_gain` and `lone_level` paths are correct, and `rules.h` is sufficient for v6 and v10.
- **Fuzzing rules_check (fuzz.c, ASan+UBSan):** of 300,000 random rule sets, 17,105 passed the check; 15,962 composed and 888 gave up cleanly on the ratio redraw. There were no memory errors, no score_check failures, no end-phase tones, no half-filled tone lists, and every composed score survived write/read unchanged. The only sanitizer report is the `end_cycles` overflow below.
- **Large cycles (edge.c):** 2,000,000,000 ticks compose without overflow under UBSan in 11 s; one more cycle is refused. Under a 150 MB memory limit the composer returns "out of memory" with 0 tones. NULL or tiny error buffers are safe.
- **Mutations (mutate.py, 25 of them):** results are in the first two findings.

Ground rules: kept. Only owned files; no global mutable state (`BUILT_IN` is `static const`); vocabulary and style are in order ("note" appears only in the sense of "remark"). No header change is needed.

With density computed over T-30 instead of T-31, the composer still produces all 625 reference lines, and check_12 passes too. Only check_20 notices, and that check exits 77 (skipped) without tar, patch or python3, without the archive, when the host rand() is not glibc, or when the old source does not build. --- [3] ROBUSTNESS @ src/compose/rules.c:108 (end_cycles check) and src/compose/slotwalk.c:129-131
PROBLEM: rules_check puts no upper limit on end_cycles. A rule set with end_cycles = INT_MAX (or INT_MAX - 1) passes the check; slotwalk_compose then computes `rules->end_cycles + COMPOSE_MIN_CYCLES_MARGIN` for its error message, which is a signed integer overflow (undefined behaviour) and prints a nonsense minimum.
EVIDENCE: Scratch `./edge_ub endmax` (edge.c, built with -fsanitize=undefined): "slotwalk.c:129:9: runtime error: signed integer overflow: 2147483647 + 2 cannot be represented in type 'int'", then "rules_check: 0" and "cycles is 500; with the rule set endmax it must be at least -2147483647". The fuzzer (fuzz.c) found the same and nothing else.
FIX: In rules_check, refuse end_cycles above a sane limit (for example 1,000,000) with a message naming end_cycles, alongside the existing slots and reps limits.

--- [4] ROBUSTNESS @ src/compose/slotwalk.c:17 and :134 (MAX_TICKS limit) versus src/score/score_text.c:104 (reader accepts cycles 1..100000000)
PROBLEM: The composer's only upper limit on cycles is slots x cycles <= 2,000,000,000 (181,818,181 cycles for v4). The score reader refuses `@ cycles` above 100,000,000. Between the two, the composer makes a score that passes score_check and is written, but cannot be read back. For v4 this needs several GB of memory, so it is a corner case, but the two limits disagree.
EVIDENCE: Scratch `./edge_ub big1 100000001` (one slot, all reps 1000, so memory stays small): "rules_check: 0", "compose: 0 ; 99901 tones", "score_check: 0", "score_read: -1 line 5: not a valid \"@ key value\" setting". Limits for v4: `./edge_ub v4big 181818182` is refused with "must be at most 181818181".
FIX: Give the composer one plain cycle limit that matches the reader (refuse cycles above 100,000,000 with a message, in addition to the tick limit), or ask the lead to raise the reader's limit. A much lower practical limit in main.c would also do.

--- [5] ROBUSTNESS @ src/compose/slotwalk.c:151-153 and :216 (the `done:` path)
PROBLEM: When composing fails after the walk has started (out of memory, or the ratio redraw giving up), the tone list is emptied but score->rules, score->cycles and score->slots keep the failed tune's values. The score is left half-filled in its settings, where the header promises these are set when the score is filled. Harmless as long as callers discard the score on error.
EVIDENCE: Scratch `( ulimit -v 150000; ./edge_ub v4big 3000000 )` prints "compose: -1 out of memory; 0 tones; rules='v4' cycles=3000000 slots=11". By contrast, a refusal before the walk (`./edge_ub v4big 181818182`) leaves rules='' cycles=0 slots=0.
FIX: Set score->rules, cycles and slots only once the walk has succeeded (score_tone_end needs score->slots during the walk, so either pass slots another way or clear the three fields again in the failure branch at `done:`).
